# Maglev Principles

## What Maglev Is

A Rust library for building JSON APIs with Axum and SQLx. It provides patterns, traits, and utilities — not a framework that owns your application.

## Core Principles

### 1. SQL lives in the application

Maglev never executes SQL queries. Apps own their schema, table names, column names, and queries. This preserves SQLx's compile-time query verification — the primary reason for choosing SQLx over an ORM.

A library crate cannot use `sqlx::query!` macros (they require `DATABASE_URL` at compile time). So library-embedded SQL always falls back to runtime-checked `sqlx::query()`, defeating the purpose.

### 2. Patterns, not persistence

For concerns that need storage (job queues, sessions, token revocation), maglev provides:
- **Traits** defining the interface (e.g. `QueueProvider`)
- **Data structures** defining the shape (e.g. `JobEntry`, `JobStatus`)
- **Orchestration logic** that operates on traits (e.g. `Worker` retry/backoff/concurrency)
- **Reference implementations** in the library (e.g. `MemoryQueue`, `RevocationList`, OAuth clients) — these can be production-ready, not just test utilities

Apps implement persistence with their own SQL, getting compile-time checking and full schema control.

### 3. Generate, don't abstract

Production-ready persistence implementations are generated by the CLI into the app's source tree. Once generated, the app owns the code. This provides:
- A working starting point with best-practice SQL (FOR UPDATE SKIP LOCKED, etc.)
- Full visibility — no hidden behavior
- Freedom to modify without fighting abstractions
- SQLx compile-time verification on the generated queries

### 4. Small trait surfaces

Traits that apps must implement should have the fewest methods possible, each mapping to one simple storage operation. The framework handles orchestration (retry, backoff, expiry); the app handles CRUD. Example: `QueueProvider` is 3 methods — insert, claim_next, update.

### 5. Framework owns universal logic; apps own domain logic

**In the framework:** Token hashing, JWT signing, password hashing, exponential backoff, worker loops, error macro codegen. These are the same in every app.

**In the app:** Table structures, session lifetimes, what fields a session has, query patterns, business rules. These vary by app.

### 6. Reduce friction at boundaries

Where the framework hands data to/from the app (e.g. `JobEntry` ↔ SQL rows), provide conversion helpers: `Display`/`FromStr` impls, `as_str()` methods, sqlx-compatible type conversions. Apps shouldn't write adapter boilerplate.

### 7. Right-sized, not minimal

Maglev includes what's universally needed for JSON APIs with Axum/SQLx. It's not trying to be minimal — it's trying to be the right size. If every API needs it (error handling, JWT, config loading), it belongs. If only some do, it's a feature flag.

## Opinionated Choices

These are load-bearing decisions, not defaults to swap out:

- **Axum** for HTTP
- **SQLx** for database (Postgres)
- **Tokio** for async runtime
- **No ORM** — direct SQL, compile-time checked
- **Serde** for serialization

## Scope

### In scope
- JWT authentication (extractors, validation traits, cookie support)
- OAuth2 client utilities (Google, GitHub, Microsoft)
- Password hashing (Argon2)
- Background jobs (traits, orchestration, scheduling)
- Email sending (SMTP)
- Error handling (`#[derive(HttpError)]`)
- Encryption utilities (AEAD)
- Config loading from environment
- Server lifecycle
- CLI code generation for persistence patterns

### Not in scope (currently)
- Database migrations
- Frontend concerns
- Full ORM / query builder
